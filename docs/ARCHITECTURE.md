# สถาปัตยกรรม

```text
Browser / Next.js
       │ HTTP API
       ▼
FastAPI ─── SPARQL ─── GraphDB 11.5
   │                       └─ Named graph แยกตามแหล่งและฉบับ
   ├──── optional ThaiLLM API: เลือก Sense / เรียบเรียงคำตอบ
   └──── ตรวจ Sense URI และ Evidence ID กับ Candidate ที่ดึงมา
       │
       └── คำตอบ + หลักฐาน + กราฟ → Browser
```

Browser ไม่ Query GraphDB โดยตรง ข้อเท็จจริงและที่มามาจาก GraphDB ส่วน ThaiLLM ใช้เพื่อเข้าใจบริบท เลือกความหมาย และเรียบเรียงคำตอบจาก Candidate/Evidence/ความสัมพันธ์ที่ส่งให้ใน API call เดียว Backend ปฏิเสธ Sense หรือ Evidence ID ที่ไม่อยู่ใน Candidate Set

เมื่อ ThaiLLM ส่งคำตอบแบบสนทนาที่ผ่านการตรวจรูปแบบพื้นฐาน ระบบแสดงคำตอบนั้นแทนเทมเพลตเดิม หากไม่ส่งหรือส่งข้อความที่ใช้ไม่ได้ ระบบยังตอบจากข้อมูลในกราฟด้วยเทมเพลตที่ปลอดภัย โดย API ระบุ `diagnostics.answer_mode` ว่าคำตอบมาจาก `model` หรือ `template` หาก ThaiLLM เรียกไม่สำเร็จ ส่ง Structured Output ผิดรูป หรืออ้าง Sense/Evidence นอก Candidate Set ระบบจะเลือกความหมายด้วย heuristic แทน และตั้ง `diagnostics.fallback_used=true` พร้อม `fallback_reason` (เช่น `llm_request_failed:HTTPStatusError:429`) เพื่อไม่ให้ผลนั้นถูกสื่อว่าเป็นของ ThaiLLM คำถามที่ขอแสดงทุกความหมาย (`define_all`) ใช้รายการจากกราฟเสมอ โดยระบุชื่อชุดข้อมูลและตัวอย่างของแต่ละความหมาย คำตอบจากโมเดลในกรณีอื่นจะต่อท้ายด้วยรายชื่อแหล่งข้อมูลเมื่อโมเดลไม่ได้ระบุเอง คำว่า “Sense/อ้างอิงตรวจแล้ว” หมายถึงการตรวจ URI/ID และแหล่งข้อมูล **ไม่ใช่** การรับรองว่าข้อความอิสระทุกประโยคของ LLM ถูกต้องทั้งหมด

เส้นทางนำเข้าคือ raw file → source mapping/adapter → normalized record → validation → RDF → named graph → automatic alignment แบบระวัง ระบบเทียบ lemma, POS และข้อความหลักฐานเป็นชุดละ 50 คำ แล้วเขียนข้อเสนอ `possiblySameSense` ลงกราฟแยกตามแหล่ง/ฉบับ เฉพาะคู่ที่ผ่านเกณฑ์ข้อความและคะแนน heuristic; คะแนนไม่ใช่ความน่าจะเป็นที่สอบเทียบแล้ว ไม่รวม source sense ต่างแหล่งเป็นข้อเท็จจริงเดียวอัตโนมัติ

เมื่อเปิด ThaiLLM คำถามจะถูกประมวลผล 2 ขั้น
1. **วิเคราะห์คำถาม (`ThaiLLMChatSenseSelector.analyze`)** — โมเดลอ่านคำถามพร้อม “คำที่กำลังคุยอยู่” แล้วตอบ JSON สั้น ๆ ว่าเป็นการคุยทั่วไปหรือถามเรื่องคำ คำเป้าหมายคืออะไร ถามเรื่องอะไร (ความหมาย, คำพ้อง/คำตรงข้าม, เปรียบเทียบแหล่ง, รากศัพท์/การออกเสียง/ชนิดคำ) และผู้ใช้ส่งประโยคมาให้ตีความหรือไม่ Backend แปลงเป็น intent แบบตายตัว เช่น ความหมาย + มีประโยค = `define` ไม่ส่งข้อความสนทนาก่อนหน้าให้ขั้นนี้ เพราะทำให้โมเดลถามซ้ำหัวข้อเดิม ใน prompt มีตัวอย่างถาม-ตอบแนบไว้ด้วย
2. **ตอบ (`select`)** — Backend ตรวจว่าคำเป้าหมายมีในคลังจริง (ถ้าผู้ใช้ระบุคำด้วย “คำว่า” จะไม่แทนด้วยคำอื่น) ดึง candidate ไม่เกิน 8 รายการ รายการละ 3 หลักฐาน และดึงความสัมพันธ์หรือรากศัพท์/คำอ่านเฉพาะเมื่อคำถามต้องใช้ จากนั้นให้โมเดลเขียนคำตอบตาม intent ที่วิเคราะห์ได้ ระบบยังตรวจรหัส Sense/Evidence และลบรหัสภายในที่หลุดมาในคำตอบ

ถ้าขั้นวิเคราะห์ล้มเหลว ระบบจะใช้กฎเดิมใน `services.py`/`thai_text.py` แทน ถ้าขั้นตอบล้มเหลว จะใช้ heuristic และ template พร้อมระบุ `fallback_reason` ทุกครั้ง ทดสอบกับระบบจริงด้วย `python scripts/eval-ask.py --repeat 2` สคริปต์นี้แยกนับความล้มเหลวที่มาจาก ThaiLLM ตอบ 5xx ไว้ต่างหาก

การหาคำเป้าหมายและบริบทใช้ตัวตัดคำไทยแบบพจนานุกรม (`backend/thailex_api/thai_text.py`) ซึ่งรวมคำจากกราฟกับรายการคำไวยากรณ์และคำถามที่ฝังในโค้ด Backend โหลดรายการคำทั้งหมดจาก GraphDB มาไว้ในหน่วยความจำ (`lexicon.py`) และโหลดใหม่ทุก `THAILEX_LEXICON_TTL_SECONDS` วินาที (ค่าเริ่มต้น 300) ชุดข้อมูลที่เพิ่งนำเข้าจึงค้นเจอหลังจากนั้นโดยไม่ต้องรีสตาร์ต คำหลัง “คำว่า” จะเทียบกับคำที่ยาวที่สุดที่มีในกราฟ ส่วนประโยคที่ไม่มี “คำว่า” จะเลือกคำเนื้อหาที่มีหลายความหมายก่อน โดยข้ามคำไวยากรณ์อย่าง “เป็น” หรือ “ของ” ถ้าข้อความมีคำเนื้อหานอกจากคำเป้าหมายและคำถาม ระบบถือว่ามีบริบท: heuristic ให้คะแนนแต่ละ Sense จากสัดส่วนคำบริบทที่พบในนิยามหรือตัวอย่าง และถ้า ThaiLLM ตอบแบบแสดงทุกความหมายทั้งที่มีบริบท ระบบจะใช้ heuristic เลือกแทนพร้อมระบุ `fallback_reason=llm_intent_overridden:define_all_with_context` ตัวตัดคำนี้ไม่ใช่ตัวตัดคำทั่วไปอย่าง PyThaiNLP คำที่ไม่มีในกราฟอาจถูกแบ่งผิดได้

โหมด “สำรวจคำ” เรียก `GET /api/entry?q=` ซึ่งคืนทุก Sense ของคำ (สูงสุด 60) แยกตามแหล่งข้อมูล พร้อมนิยาม ตัวอย่างและคำแปล การออกเสียง รูปคำ รากศัพท์ คำสัมพันธ์ และข้อเสนอเชื่อมความหมายข้ามแหล่งพร้อมสถานะตรวจ รายละเอียดทั้งหมดดึงด้วย batch query สองชุด ถ้าไม่พบคำ API จะเสนอคำใกล้เคียงแทน

การเพิ่มชุดข้อมูลใหม่ไม่ต้องแก้หน้าเว็บ หาก adapter สร้าง RDF ตาม schema ที่ API อ่านได้แล้ว การ import ผ่านสคริปต์จะเรียก alignment อัตโนมัติและหน้าเปรียบเทียบอ่านข้อเสนอได้ แต่ยังต้องตรวจคุณภาพเป็นตัวอย่างและให้คนตัดสินข้อที่ต้องการประกาศว่า `exactMatch` หรือ `closeMatch` โดยผลตรวจอยู่กราฟแยกที่การรันอัตโนมัติไม่เขียนทับ

สถานะต้นแบบ: LLM เป็น optional; heuristic เป็นค่าเริ่มต้นสำหรับการรันในเครื่อง คำตอบแบบสนทนาจากโมเดลต้องตั้งค่า ThaiLLM ก่อน ไม่ควรสื่อว่าผล heuristic เป็นผลจาก ThaiLLM
